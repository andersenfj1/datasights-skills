# Getting Data In

How to get data in front of DataSights models and widgets. Three paths, in order of preference: point a Source at a database that already has the data, import a CSV into an existing Source's database, or convert other formats (PDF, XLSX, pasted tables) to clean CSV first.

Step-by-step UI instructions for the Sources page live in [modules/sources.md](modules/sources.md) — this file does not repeat them. It covers what that doc lacks: exact limits, identifier rules, the all-TEXT caveat, and how to prepare data.

---

## 1. Decision tree

```text
Where is the data right now?
│
├─ Already in a MySQL or PostgreSQL database
│    └─► Add a Source pointing at it (section 2). Done — no import needed.
│
├─ A CSV file (or something you can trivially save as CSV)
│    ├─ ≤ 10 MB and ≤ 100,000 data rows
│    │    └─► CSV import, sync or async path (section 3)
│    ├─ ≤ 512 MB and ≤ 100,000 data rows
│    │    └─► CSV import, async job path only (section 3.2)
│    └─ > 100,000 rows (any size)
│         └─► CSV import CANNOT take it — the row cap applies to both paths.
│             Load it into the database directly (LOAD DATA INFILE / \copy),
│             then just add/point a Source at that table.
│
└─ PDF, XLSX, Google Sheet, pasted table, screenshot, etc.
     └─► Convert to clean CSV in chat first (section 4), then re-enter
         this tree at the CSV branch. If it is large or recurring,
         skip CSV and load into a real database instead.
```

Key facts driving the tree:

| Limit | Value |
|---|---|
| Sync endpoint byte cap | `10 * 1024 * 1024` (10 MB) |
| Data-row cap — **both** sync and async | `100_000` |
| Async job byte cap | `512 * 1024 * 1024` (512 MB) |
| Rows per INSERT batch | `500` |
| How long async job status is pollable | 6 hours |

The 512 MB async path raises the *byte* limit, not the *row* limit. "Big" CSVs that fit the async path are wide/texty ones, not million-row ones.

## 2. Source setup essentials

A Source is a studio-scoped database connection. Follow the literal click-path in [modules/sources.md → "Add A Source"](modules/sources.md); the essentials it does not spell out:

**Per-type fields**:

| Field | MySQL | PostgreSQL | Notes |
|---|---|---|---|
| Name | required | required | Display name only |
| Host | required | required | Hostname or IP; must be reachable *from the DataSights server*, not your laptop |
| Port | required | required | Typical: `3306` (MySQL), `5432` (PostgreSQL) — shown as placeholders, always entered explicitly |
| Database | required | required | Schema/database name |
| Username | required | required | Prefer a least-privilege, read-only account unless writeback is needed |
| Password | optional | optional | Stored AES-256-GCM-encrypted; hidden after save, only re-entered to replace |
| Require SSL | — | checkbox | Postgres only; the server ignores `requireSsl` for MySQL |

Microsoft SQL Server exists as a legacy source type (`mssql`, typical port 1433) but is not offered in the add-source selector and **rejected by CSV import** — treat sources as MySQL/PostgreSQL only.

**API shape** (for scripted setup): `POST /api/sources` (alias `POST /api/sources/create`) with JSON body `{ type: "mysql" | "postgres", studioId, name, database, host, port, username, password, requireSsl }`. Requires edit access on the studio.

**Test Connection** — always run it before saving. `POST /api/sources/test` (alias `/test-connection`) with `{ type, host, port, username, password, database, requireSsl }` plus **either** `studioId` (new source) **or** `sourceId` (editing an existing one) — omitting both returns 400 `"Studio id or source id is required for testing"`. When editing an existing source and leaving password blank, the stored decrypted password is used automatically. Success returns `{ ok: true }` (UI shows **Connection successful.**); any connectivity failure returns 500 `{ "error": "Failed to connect to source" }` — check host/port/credentials and network reachability from the app server.

## 3. CSV import in depth

CSV import loads a file into a table **inside an existing MySQL or PostgreSQL Source's database**. It is not a standalone upload store — a Source must exist first. Requires edit access. UI click-paths: [modules/sources.md → "Import A CSV Into A New Table" / "Append A CSV To An Existing Table"](modules/sources.md).

### 3.1 Create vs append

**Create mode** (`mode: "create"`, UI: **Create New Table**):
- Fails with 409 `Table "X" already exists.` (`TABLE_EXISTS`) if the table name is taken.
- Creates the table and inserts all rows. A header-only CSV is accepted and creates an empty table.
- **MySQL** table shape: `` `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY `` plus every CSV column as `TEXT NULL`.
- **PostgreSQL** table shape: `"id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` plus every CSV column as `TEXT NULL`, created in schema `public`.
- Column names are derived from headers via normalization (3.3). A CSV column that normalizes to `id` is renamed `id_1` to avoid the reserved auto `id` column.
- Column-type inference is **not applied** — every created data column is literally `TEXT`. See the big caveat in 3.4.

**Append mode** (`mode: "append"`, UI: **Append Existing**):
- Target table must exist: 404 `Table "X" was not found.` (`TABLE_NOT_FOUND`) otherwise.
- Auto-generated columns (MySQL `auto_increment`; Postgres identity or `nextval(...)` default) are excluded from matching and never written.
- CSV headers are normalized (same rules as create) then matched **case-insensitively** against the remaining table columns. By default the sets must match exactly, or you get 400 `CSV columns do not match the target table columns.` (`COLUMN_MISMATCH`) with `details.missingInCsv` / `details.extraInCsv`.
- `allowMissingColumnsAsNull: true` — proceed when the CSV is missing some table columns (filled with `NULL`), **as long as there are no extra CSV columns**.
- `allowColumnMismatch: true` — proceed with any mismatch: matching columns inserted, missing table columns `NULL`, extra CSV columns ignored. This is what the UI's **Yes, continue** confirmation sends.
- Appending a CSV with zero data rows fails: 400 `CSV must include at least one data row when appending.` (`CSV_NO_DATA_ROWS`).

**Both modes:** rows insert in batches of 500 inside a transaction; empty/whitespace-only cells are stored as SQL `NULL` (not `''`). If a batch INSERT fails, the runner retries row-by-row to pinpoint the failure, then raises 400 `CSV import failed while inserting rows.` (`ROW_INSERT_FAILED`) with `details.row` = the CSV **file line number counting the header as line 1**, and `details.column` when the DB error names one. On failure everything rolls back — except on MySQL in create mode, where `CREATE TABLE` implicitly commits: a failed create-mode import can leave the new table behind (empty or partial). Drop it before retrying, or the retry hits `TABLE_EXISTS`.

### 3.2 Sync vs async endpoints

- **Sync:** `POST /api/sources/:id/csv/import`, JSON body `{ mode, tableName, csvText, fileName?, allowMissingColumnsAsNull?, allowColumnMismatch? }`. 10 MB / 100,000 rows. Responds only when done.
- **Async (what the UI uses):** `POST /api/sources/:id/csv/import/jobs`, multipart form with the file in field `file` plus text fields `mode`, `tableName`, `fileName?`, `allowMissingColumnsAsNull?`, `allowColumnMismatch?`. 512 MB / 100,000 rows. Returns 202 with a `jobId`; poll `GET /api/sources/:id/csv/import/jobs/:jobId` (UI polls every 1 s for up to 60 min). Job `status` is `queued | processing | completed | failed`; `progress` reports `phase`, `rowsParsed`, `rowsInserted`. Jobs are in-memory and vanish after 6 h (or a server restart) — after that, polling returns 404 `CSV import job not found.`

### 3.3 Identifier rules

- **Table name** must match `/^[A-Za-z_][A-Za-z0-9_]*$/`, or the API rejects it: `"Table name must start with a letter or underscore and contain only letters, numbers, or underscores."`
- **Duplicate-header check** runs on trimmed, lowercased headers *before* normalization — `Name` and `name ` collide (400 `Duplicate column names found in CSV header.`, `CSV_DUPLICATE_HEADERS`, `details.duplicates`; a blank header shows as `(blank)`).
- **Column names in create mode** come from header normalization: trim → lowercase → every run of non-`[a-z0-9]` becomes `_` → collapse `_` runs → strip leading/trailing `_`; an empty result becomes `col_<position>` (1-based); a leading digit gets a `col_` prefix (`2024 Revenue` → `col_2024_revenue`); post-normalization duplicates get `_2`, `_3`, … suffixes; a collision with the reserved `id` becomes `id_1`.

Practical consequence: `Total (DKK)` silently becomes `total_dkk`. Name columns yourself in the CSV so there are no surprises — those names flow through model aliases into widget field bindings.

### 3.4 THE BIG CAVEAT: everything is TEXT

Created tables have **every data column as `TEXT`** plus an auto `id`. Nothing is typed. Therefore **every numeric or date operation in a model over an imported table needs an explicit cast** (`CAST` / `STR_TO_DATE` on MySQL, `::type` on Postgres). The model's SELECT is where typing happens — DataSights wraps model SQL as `SELECT ... FROM (<model_query>) AS base`, so the aliases you cast under become the widget-bindable field names.

**Worked example.** A messy export:

```csv
Order ID,Customer Name,Order Date,Total (DKK),Discount %
1001,Acme A/S,06/01/2026,"kr 1.234,50",10%
1002,Beta ApS,07/01/2026,"kr 890,00",
```

Clean it first (see section 4 for the rules) — snake_case headers you chose deliberately, ISO dates, bare numbers, units moved into the column name, missing value left empty:

```csv
order_id,customer_name,order_date,total_dkk,discount_pct
1001,Acme A/S,2026-01-06,1234.50,10
1002,Beta ApS,2026-01-07,890.00,
```

Import it: **Sources → Import CSV** → pick the Source → **Create New Table** → choose the file → table name `orders_import` → **Import CSV**. Resulting MySQL table: `id BIGINT UNSIGNED AUTO_INCREMENT PK`, then `order_id`, `customer_name`, `order_date`, `total_dkk`, `discount_pct` — **all `TEXT`**. The empty discount cell is `NULL`.

Model SQL over it — MySQL:

```sql
SELECT
  CAST(order_id AS UNSIGNED)          AS order_id,
  customer_name                       AS customer,
  STR_TO_DATE(order_date, '%Y-%m-%d') AS order_date,
  CAST(total_dkk AS DECIMAL(12,2))    AS total_dkk,
  CAST(discount_pct AS DECIMAL(5,2))  AS discount_pct
FROM orders_import
```

PostgreSQL equivalent: `order_id::bigint`, `order_date::date`, `total_dkk::numeric(12,2)`, `discount_pct::numeric(5,2)`. (No `NULLIF` needed — the importer already stored blanks as `NULL`.)

**What breaks without the casts** — the symptoms the user actually sees:

- **PostgreSQL:** hard error. `SUM(total_dkk)` on a text column fails the model preview / widget query with `function sum(text) does not exist`. AVG/date_trunc similarly. The widget shows the query error; nothing renders.
- **MySQL:** silent wrongness. Sorting `total_dkk` is lexicographic — `"890.00"` sorts *after* `"1234.50"`; top-N tables and axis ordering are garbage. A text `order_date` on a chart's time axis is treated as a plain category (no date grouping, gaps not respected). Aggregations implicitly coerce and any stray non-numeric character silently truncates to the leading numeric prefix (or 0), producing wrong totals with no error.

Also remember the auto `id` column exists: `SELECT *` in a model over an imported table exposes `id` as a widget field. Fine for writeback keys, noise otherwise — prefer an explicit column list.

## 4. Converting PDFs, XLSX, and pasted tables in chat

DataSights only ingests CSV. When the user hands you (Claude) a PDF, spreadsheet, screenshot, or pasted table, produce a clean CSV **in chat** before importing. Produce it to this spec — each rule maps to a hard validator or the TEXT caveat above:

1. **Exactly one header row**, no title lines, no merged-cell banners, no footer/total rows mixed into data. (`CSV_NO_HEADER` / garbage rows otherwise.)
2. **Headers**: lowercase `snake_case`, ASCII, each matching `[a-z_][a-z0-9_]*`, unique, no blank headers. Put units in the name (`total_dkk`, `discount_pct`, `weight_kg`) instead of symbols in the values.
3. **Numbers**: plain digits with `.` as decimal point. **No thousands separators** (`1234.50`, never `1,234.50` or `1.234,50`), no currency symbols, no `%`, no `kr`/`$`/`€`, no parentheses-for-negative (use `-`).
4. **Dates**: ISO — `YYYY-MM-DD` for dates, `YYYY-MM-DD HH:MM:SS` for timestamps. Never `06/01/2026` (ambiguous) or `Jan 6, 2026`.
5. **Missing values**: leave the cell completely empty (imports as `NULL`). Never write `N/A`, `-`, `null`, or `0` for missing.
6. **Quoting** (RFC 4180): double-quote any field containing a comma, double quote, or newline; escape embedded quotes by doubling (`"Acme ""North"" A/S"`). Don't pad cells with spaces — the importer preserves them.
7. **Consistent column count on every row.** The parser does not tolerate ragged rows; one of them fails the whole import (`CSV_COLUMN_COUNT_MISMATCH`, `details.row` tells you which line).
8. **Encoding**: UTF-8. A BOM is tolerated; empty lines are skipped.

Then hand the user the CSV plus a ready-made model SQL with the casts (as in 3.4) — never one without the other.

**When to recommend a real database load instead of CSV import:**

- **More than 100,000 rows** — CSV import cannot take it on either path; load via `LOAD DATA INFILE` (MySQL) / `\copy` (Postgres) into the Source's database, with proper column types, then models query it directly with no casts needed.
- **Recurring feeds** (daily exports, ongoing syncs) — CSV import has no scheduling or dedup; a repeated append just duplicates rows. Land the data in the DB by pipeline and point a Source at it.
- **Type-critical or index-needing data** — a hand-created table with real `DECIMAL`/`DATE` columns and indexes beats an all-TEXT import that pushes casting into every model.
- Files between 10 MB and 512 MB are fine via the async job path (3.2) as long as they respect the row cap.

## 5. Writeback note

Sources are read-only by default. A per-source **Allow data-grid writeback** toggle lets editable data-grid widgets and form-style flows save changes back through the Source's stored credentials:

- **Studio administrators only** — the API rejects non-admin changes with `"Only studio admins can change writeback access"` (`PATCH /api/sources/:id`, body field `writebackEnabled`); editors don't see the toggle.
- **MySQL and PostgreSQL sources only.**
- Turning it on does not make anything editable by itself — it's the source-level gate that per-widget editing later opts into.
- Writeback uses the same stored DB credentials as reads, so the database account's own grants are the real ceiling; use a least-privilege account.

Full flow and safety guidance: [modules/sources.md → "Allow Data-grid Writeback"](modules/sources.md).

## 6. Troubleshooting import errors

Exact strings returned by the API (`error` field; `code`/`details` where noted). Async-path failures surface the same payloads inside the job's `error` object.

| HTTP | `error` message | `code` | What it means / fix |
|---|---|---|---|
| 400 | `Mode must be create or append.` | — | Bad `mode` value in the request |
| 400 | `Table name must start with a letter or underscore and contain only letters, numbers, or underscores.` | — | Name fails `/^[A-Za-z_][A-Za-z0-9_]*$/` — no spaces, dashes, dots, or leading digits |
| 400 | `CSV content is required.` | `CSV_TEXT_REQUIRED` | Sync path called without `csvText` string |
| 413 | `CSV exceeds 10 MB limit.` | `CSV_TOO_LARGE` | Sync byte cap — switch to the async job path |
| 413 | `CSV exceeds 512 MB limit.` | `CSV_TOO_LARGE` | Async byte cap — load into the DB directly instead |
| 400 | `CSV exceeds 100,000 row limit.` | `CSV_TOO_MANY_ROWS` | Row cap (both paths) — split the file or load into the DB directly |
| 400 | `CSV file is empty.` | `CSV_EMPTY` | Empty/whitespace-only file |
| 400 | `CSV header row is missing.` | `CSV_NO_HEADER` | First row absent/blank — ensure exactly one header row |
| 400 | `Duplicate column names found in CSV header.` | `CSV_DUPLICATE_HEADERS` | Case-insensitive after trim; `details.duplicates` lists them (`(blank)` = empty header) |
| 400 | `CSV row has inconsistent column count.` (or the CSV parser's own message) | `CSV_COLUMN_COUNT_MISMATCH` | Ragged row; `details.row` = offending line. Usually an unquoted comma |
| 400 | *(parser message)* / `Could not parse CSV.` | `CSV_PARSE_FAILED` | Malformed quoting/encoding — regenerate per section 4 |
| 409 | `Table "X" already exists.` | `TABLE_EXISTS` | Create mode into an existing table — pick a new name, or drop the leftover from a failed MySQL create (see 3.1) |
| 404 | `Table "X" was not found.` | `TABLE_NOT_FOUND` | Append target missing (or wrong case/schema — Postgres append looks in `public`) |
| 400 | `CSV columns do not match the target table columns.` | `COLUMN_MISMATCH` | `details.missingInCsv` / `details.extraInCsv`; fix headers, or pass `allowMissingColumnsAsNull` / `allowColumnMismatch` (UI: **Yes, continue**) |
| 400 | `CSV must include at least one data row when appending.` | `CSV_NO_DATA_ROWS` | Header-only CSV in append mode |
| 400 | `CSV import failed while inserting rows.` | `ROW_INSERT_FAILED` | DB rejected a row; `details.row` = CSV line number (header = line 1), `details.column` when known |
| 400 | `CSV import is currently supported only for MySQL and PostgreSQL sources.` | `UNSUPPORTED_SOURCE_TYPE` | Source is `mssql`/unknown — import needs a MySQL/PG source |
| 400 | `Missing required connection details` | — | Source record lacks host/database/username — edit the source |
| 403 | `Not authorized to import CSV into this source` | — | Import needs **edit** access on the source's studio |
| 404 | `Source not found` | — | Bad/inactive source id, or its studio is deleted |
| 404 | `CSV import job not found.` | — | Async job expired (6 h retention), server restarted, or polled with a different user/source than created it |
| 500 | *(raw SQL message)* / `Failed to import CSV.` | — | Unexpected DB error — the message is the raw text from the database driver; check connectivity and DB-side constraints |

After any failed import, remember the transaction semantics from 3.1: Postgres rolls back completely; MySQL create-mode may leave the table behind.
